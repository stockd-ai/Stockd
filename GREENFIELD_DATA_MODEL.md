## Data Model Philosophy

The Stockd schema should be designed around **tenant isolation, inventory auditability, reversible ingestion, and deterministic calculations**. Every restaurant-facing record belongs to an organization, and most operational records belong to a location. The schema should make it impossible to change inventory silently. Current stock is a materialized state derived from receipts, counts, waste, sales depletion, adjustments, and rollbacks; it is not the primary source of truth.

Supabase RLS should be enabled on all exposed tables because Supabase recommends RLS for tables in exposed schemas and evaluates table policies whenever rows are accessed.[1] Application writes that alter inventory should go through SQL RPC functions or Edge Functions, but RLS must still protect the underlying tables as defense in depth.

## Naming and Global Conventions

| Convention | Recommendation |
|---|---|
| Primary keys | `id uuid primary key default gen_random_uuid()` for all domain tables. |
| Tenant keys | `org_id uuid not null references organizations(id)` on all tenant-scoped tables; `location_id` when location-specific. |
| Timestamps | `created_at`, `updated_at`, `deleted_at` where soft deletion is needed. Use database defaults. |
| Audit fields | `created_by`, `updated_by`, and workflow-specific actor fields where relevant. |
| Money | Store currency amounts in integer cents or `numeric(12,4)` for unit costs; never use floats. |
| Quantities | Store canonical quantities in base units as `numeric(14,4)` and preserve original quantity/unit fields. |
| Status | Use constrained text enums or Postgres enums with clear lifecycle transitions. |
| Source tracking | Imported rows include `import_job_id`, `source_file_path`, `source_row_number`, and `source_hash` where relevant. |
| RLS | Policies should join through `organization_memberships` and optionally location permissions. |

## Entity Relationship Overview

| Domain | Core Tables | Source of Truth |
|---|---|---|
| Tenant and identity | `organizations`, `locations`, `profiles`, `organization_memberships` | Supabase Auth user plus membership records. |
| Vendor catalog | `vendors`, `vendor_product_aliases` | User-confirmed vendor and alias records. |
| Menu and recipe | `ingredients`, `menu_items`, `bom_recipes`, `unit_conversions` | Confirmed ingredient and BOM records. |
| Ingestion | `import_jobs`, `import_errors`, `sales_imports`, `sales_line_items_raw`, `sales_daily_aggregates` | Import jobs plus committed raw records. |
| Inventory | `inventory_transactions`, `inventory_on_hand`, `count_sheets`, `vendor_receipts`, `receipt_items`, `waste_logs` | Ledger transactions; on-hand is materialized. |
| Planning | `forecasts`, `reorder_recommendations` | Versioned deterministic runs. |
| AI and governance | `ai_conversations`, `audit_log` | Conversation and immutable audit history. |

## Table Specifications

|---|---|---|---|---|---|---|---|
| `organizations` | Represents a customer account or restaurant group. | `id`, `name`, `slug`, `billing_status`, `timezone`, `created_at`, `updated_at`, `deleted_at`. | Parent of locations, memberships, vendors, ingredients, imports, and all operational data. | Unique `slug`; index `billing_status`. | `slug` unique; `name` non-empty; soft-delete only if no active pilot or after export. | Members can select their org; only owners/admins can update; service role can manage billing state. | Created during signup; rarely deleted; supports future multi-location. |
| `locations` | Represents a restaurant operating site. | `id`, `org_id`, `name`, `address`, `timezone`, `service_days`, `default_order_cutoff_time`, `active`, timestamps. | Belongs to organization; parent of sales, inventory, counts, receipts, forecasts. | `(org_id, active)`, `(org_id, name)`. | `org_id` required; timezone defaults to org; name unique per org. | Members of org can select; location-level restrictions can be added later. | Alpha supports one active location, but schema supports more. |
| `profiles` | Application profile extending Supabase Auth users. | `id` matching auth user, `display_name`, `email`, `phone`, `avatar_url`, `last_active_at`, timestamps. | Linked to memberships and audit actors. | Unique `email`; index `last_active_at`. | `id` must equal `auth.uid()` for self-created profile. | Users can select/update own profile; service role can create on auth hook. | Keep minimal; avoid storing sensitive identity data not needed. |
| `organization_memberships` | Maps users to organizations and roles. | `id`, `org_id`, `user_id`, `role`, `status`, `invited_by`, `accepted_at`, timestamps. | Joins organizations and profiles. | Unique `(org_id,user_id)`; `(user_id,status)`; `(org_id,role)`. | Role in `owner/admin/manager/staff/viewer`; at least one owner enforced by function. | Users can see own memberships; owners/admins manage members; policies for all tenant tables reference this table. | Role changes create audit log entries. |

| `menu_items` | Sellable POS/menu items imported or manually created. | `id`, `org_id`, `location_id`, `pos_item_id`, `name`, `category`, `price_cents`, `active`, `source`, timestamps. | Parent of BOMs and sales line items. | `(location_id,active)`, `(location_id,pos_item_id)`, search on name. | Unique `pos_item_id` per location when present. | Org/location members read; managers/admins edit. | Imported menu items require review before BOM completeness is assumed. |
| `bom_recipes` | Bill of materials linking menu items to ingredient usage. | `id`, `org_id`, `location_id`, `menu_item_id`, `ingredient_id`, `quantity`, `unit`, `canonical_qty`, `canonical_unit`, `yield_pct`, `status`, `draft_source`, `confirmed_by`, timestamps. | Joins menu items and ingredients. | `(menu_item_id)`, `(ingredient_id)`, `(status)`. | Positive quantity; confirmed rows require unit conversion to canonical unit. | Members read; managers/admins confirm; AI can create draft rows through function only. | Versioning can be added later; alpha uses status plus audit log. |
| `unit_conversions` | Converts between units for ingredients and categories. | `id`, `org_id nullable`, `ingredient_id nullable`, `from_unit`, `to_unit`, `factor`, `conversion_type`, `confidence`, `source`, `confirmed_by`, timestamps. | Used by BOM, receipts, counts, waste, imports. | `(ingredient_id,from_unit,to_unit)`, `(org_id,conversion_type)`. | Factor positive; either global/category or ingredient-specific scope. | Global rows readable; org rows scoped; only managers/admins confirm org conversions. | Ingredient-specific density conversions require human confirmation. |
| `sales_imports` | Header for committed sales data batches. | `id`, `org_id`, `location_id`, `import_job_id`, `business_date_start`, `business_date_end`, `source_system`, `row_count`, `committed_at`, `committed_by`. | Parent for raw sales line items and aggregates. | `(location_id,business_date_start)`, `(import_job_id)`. | One committed sales import per job; date range valid. | Members read; only import commit RPC writes. | Rollback marks import reversed and removes derived effects via reversing records. |
| `sales_line_items_raw` | Preserves raw menu sales rows from POS/CSV. | `id`, `org_id`, `location_id`, `sales_import_id`, `business_date`, `source_row_number`, `pos_item_id`, `menu_item_id`, `item_name_raw`, `quantity_sold`, `gross_sales_cents`, `discount_cents`, `tax_cents`, `source_hash`. | Belongs to sales import and optionally menu item. | `(location_id,business_date)`, `(menu_item_id,business_date)`, unique `(sales_import_id,source_hash)`. | Quantity non-negative; money fields integer cents. | Members read; writes through import commit only. | Never overwritten; corrected through replacement import or rollback. |
| `sales_daily_aggregates` | Speeds forecasting and dashboards. | `id`, `org_id`, `location_id`, `business_date`, `menu_item_id`, `quantity_sold`, `gross_sales_cents`, `net_sales_cents`, `source_import_ids`, `computed_at`. | Derived from raw line items. | Unique `(location_id,business_date,menu_item_id)`, `(business_date)`. | Aggregates must be rebuilt idempotently. | Members read; service/RPC writes. | Can be recomputed; not primary evidence. |
| `inventory_transactions` | Immutable ledger of all inventory-changing events. | `id`, `org_id`, `location_id`, `ingredient_id`, `transaction_type`, `quantity_delta`, `unit`, `canonical_delta`, `canonical_unit`, `source_type`, `source_id`, `reason`, `occurred_at`, `created_by`, `reversal_of_transaction_id`, timestamps. | References ingredient and source records such as receipts/counts/waste/imports. | `(ingredient_id,occurred_at)`, `(location_id,occurred_at)`, `(source_type,source_id)`. | Non-zero delta; reversal references original; no hard deletes. | Members read; writes only through privileged RPC functions; staff writes indirectly via workflows. | Source of truth for inventory history. |
| `inventory_on_hand` | Materialized current stock for fast screens. | `id`, `org_id`, `location_id`, `ingredient_id`, `canonical_qty`, `canonical_unit`, `last_transaction_at`, `last_count_at`, `updated_at`. | One row per ingredient/location. | Unique `(location_id,ingredient_id)`, `(location_id,canonical_qty)`. | Quantity can be negative but flagged; unit matches ingredient base unit. | Members read; service/RPC writes only. | Rebuildable from ledger; show freshness and last count. |

| `import_errors` | Row-level or document-level ingestion errors. | `id`, `org_id`, `import_job_id`, `source_row_number`, `severity`, `field_name`, `message`, `raw_value`, `resolution_status`, `resolved_by`, timestamps. | Belongs to import job. | `(import_job_id,severity)`, `(resolution_status)`. | Severity constrained; errors preserved after rollback. | Same visibility as import job. | Drives import repair UI and support diagnostics. |
| `ai_conversations` | Stores copilot sessions, turns, tool calls, and confirmations. | `id`, `org_id`, `location_id`, `user_id`, `title`, `status`, `messages jsonb`, `tool_calls jsonb`, `model_provider`, `model_name`, `redaction_version`, timestamps. | References user/org/location; may link to audit entries. | `(user_id,updated_at)`, `(location_id,updated_at)`, GIN on metadata if needed. | Sensitive data redacted where possible; confirmed actions require audit log link. | Users see own conversations; admins may see org conversations depending on privacy setting. | Retention policy should be explicit before pilots. |

## RLS Pattern

The default read policy for tenant tables should check whether the authenticated user has an active membership in the row's organization. Write policies should be stricter and often replaced by RPC-only writes. A representative pattern is:

> A user can select rows where `exists (select 1 from organization_memberships m where m.org_id = row.org_id and m.user_id = auth.uid() and m.status = 'active')`.

For write operations, policies should require an active membership role of `owner`, `admin`, or `manager`, and transactional functions should validate the same role internally. This redundancy is deliberate because browser clients, Edge Functions, and future integrations may access data through different paths.

## Lifecycle and Data Retention

Operational data should be retained for the customer lifetime because historical sales, receipts, counts, and waste are needed for forecasting and analysis. If a customer churns, Stockd should support export and deletion according to the customer agreement. In alpha, deletion can be manual but documented. In beta, export and delete workflows should become productized admin operations.

Imported source files and AI conversation logs deserve special attention. Restaurants may upload invoices and sales files that contain vendor pricing and sensitive commercial data. These artifacts should remain in private storage, should be scoped by organization, and should be accessible only through signed URLs or authorized application views.[2]
